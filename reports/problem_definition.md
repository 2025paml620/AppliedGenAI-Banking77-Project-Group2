# Problem Definition and Application Contract

## 1. Problem Statement

This project develops an educational banking customer-support assistant using a pretrained causal language model. Given a customer's natural-language query, the application predicts the likely banking intent, generates a relevant customer-facing response, and optionally suggests an appropriate action.

The project explores prompting strategies, decoding controls, structured outputs, simulated tool/function calling, evaluation, and responsible use.

## 2. Target User

The target user is a banking customer who asks a question or reports a banking-related problem in natural language.

Representative scenarios include questions about card arrival, card loss, transfers, and declined transactions.

## 3. Input Contract

The application accepts the following input:

```json
{
  "query": "I am still waiting on my card",
  "context": null
}
```

- `query`: Required string containing the customer's message.
- `context`: Optional additional context, such as relevant conversation history. It may be `null`.

The initial baseline will use the customer query as its primary input. Context handling may be expanded as the application develops.

## 4. Output Contract

The application is expected to return:

```json
{
  "intent": "card_arrival",
  "response": "I can help you check the next steps for your card.",
  "suggested_action": null
}
```

- `intent`: Predicted intent, using one of the 77 Banking77 intent labels.
- `response`: Customer-facing response generated by the assistant.
- `suggested_action`: Optional suggested action, represented as `null` when no action is proposed.

The example illustrates the output structure. Its response is not a verified banking-policy statement.

The final machine-readable schema, field validation, and tool/function interface will be implemented in Part 3.

## 5. System Boundaries and Responsible Use

This application is an educational prototype, not a production banking service.

- It will not connect to real bank accounts.
- It will not process real financial transactions.
- It will not use real customer credentials.
- Banking tool/function calls will be simulated.
- A predicted intent or suggested action does not authorize an operation.
- Generated responses must be evaluated for relevance, unsupported claims, and safety.

## 6. Integration Contract

Part 1 defines the problem, inputs, outputs, and evaluation expectations.

Part 2 implements the pretrained LLM baseline, prompt variants, and decoding experiments.

Part 3 implements structured-output validation, reusable prompt templates, and simulated tool/function calling.

Part 4 integrates the components and evaluates the end-to-end application.

Any change to the agreed input or output fields should be documented and communicated to the team.
